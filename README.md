G4GO uses Geant4 as its physics and geometry foundation and CUDA/OptiX to accelerate optical-photon transport.

The project targets single-crystal optical detector cells. It provides unified CPU/GPU optical backends, a Geant4 event adapter, and ROOT ntuple output. The GPU backend performs batched optical-photon transport while Geant4 continues to handle particle interactions, geometry, material properties, event management, and output writing.

## Features

- Detector construction, primary-particle generation, energy deposition, and CPU optical transport with Geant4.
- GPU optical-photon transport with CUDA and NVIDIA OptiX 9.1.
- `auto`, `cpu`, and `gpu` backend selection.
- ROOT ntuple output for `CrystalHit` and `SensorHit`.
- Optical-boundary unit tests, an end-to-end smoke test, and CPU/GPU optical regression tests with TOF and sensor occupancy checks.

## Backends

| Backend | Optical-photon processing | Use cases | Failure behavior |
| --- | --- | --- | --- |
| `auto` | Select OptiX when the GPU backend is built; otherwise select Geant4 | General runs and smoke tests | Report runtime OptiX errors directly |
| `cpu` | Native Geant4 optical tracking | Baselines and systems without an NVIDIA GPU | Report Geant4 errors directly |
| `gpu` | Capture optical photons generated by Geant4 and transport them with OptiX | GPU validation, performance tests, and regression tests | Fail directly when OptiX is unavailable |

## Dependencies

### Core build

| Dependency | Requirement | Purpose |
| --- | --- | --- |
| CMake | 3.24 or newer | Configure and build |
| C++ compiler | C++20 support | Compile host code |
| Geant4 | 11.4.2 or compatible | Physics, geometry, events, and analysis |
| Git and network access | Available during the first configure step | Fetch CLI11 with `FetchContent`; fetch OptiX headers when enabled |

### GPU backend

- An NVIDIA GPU and an NVIDIA driver newer than R590. The OptiX runtime is provided by the NVIDIA driver.
- CUDA Toolkit 12.0 or newer, including `nvcc` and `bin2c`.
- OptiX 9.1 development headers fetched by CMake from `NVIDIA/optix-dev`; the full OptiX SDK is optional for G4GO.
- `G4GO_CUDA_ARCHITECTURE` matching the target GPU compute capability.

### Testing and output inspection

- Bash for CPU/GPU regression orchestration.
- ROOT command-line tools for regression comparison; `rootls` can inspect output files.
- `clang-format` is optional; when detected, CMake creates formatting targets.

## Build

### Enable OptiX

~~~bash
cmake -S . -B build \
  -DG4GO_BUILD_UIVIS=OFF \
  -DG4GO_ENABLE_OPTIX=ON
cmake --build build -j
~~~

Set `G4GO_CUDA_ARCHITECTURE` to the target GPU's numeric compute capability, such as `89` for `compute_89`.

### Geant4 backend only

~~~bash
cmake -S . -B build \
  -DG4GO_BUILD_UIVIS=OFF \
  -DG4GO_ENABLE_OPTIX=OFF
cmake --build build -j
~~~

### Common CMake options

| Option | Default | Description |
| --- | --- | --- |
| `G4GO_BUILD_UIVIS` | `ON` | Build Geant4 UI and visualization support |
| `G4GO_ENABLE_OPTIX` | `ON` | Try to build the CUDA/OptiX backend |
| `G4GO_CUDA_ARCHITECTURE` | `120` | CUDA compute architecture for the OptiX device program |
| `G4GO_ENABLE_FORMAT_TARGETS` | `ON` | Detect and create clang-format targets |
| `G4GO_ENABLE_CLANG_TIDY` | `OFF` | Enable clang-tidy during compilation |
| `BUILD_TESTING` | `ON` | Register CTest tests |

During configuration, `scripts/` is copied to `build/scripts/` and test files are copied to `build/test/`. Re-run CMake after changing these files to synchronize the build directory.

Install the executable with:

~~~bash
cmake --install build --prefix /path/to/prefix
~~~

## Quick start

Run the single-photon optical test macro from the build directory:

~~~bash
cd build
./g4go --backend auto scripts/run_optical_test.mac
~~~

Use `--backend cpu` or `--backend gpu` to select a backend explicitly.

With `G4GO_BUILD_UIVIS=ON`, start interactive visualization from the directory containing `vis.mac`:

~~~bash
cd build/scripts
../g4go
~~~

## Command-line interface

~~~text
g4go [OPTIONS] [macro]
~~~

| Option | Default | Description |
| --- | --- | --- |
| `-h, --help` | — | Show help |
| `--backend auto\|cpu\|gpu` | `auto` | Select the optical-photon transport backend |
| `--seed UINT64` | `42` | Set Geant4 and OptiX random seeds |
| `--threads UINT32` | `0` | Number of Geant4 workers; `0` uses the detected CPU core count |
| `--batch-photons UINT32` | `1000000` | Target photon count per GPU batch |
| `--batch-timeout-ms UINT32` | `10` | Maximum wait for more events before emitting a GPU batch |
| `--max-photons UINT32` | `5000000` | Maximum photons captured per event |
| `--max-bounces UINT32` | `4096` | Maximum boundary interactions per photon |
| `--perf-diagnostics` | disabled | Emit capture, scheduler, CUDA-stage, OptiX, and transport-counter diagnostics |
| `--mesh-rotation-steps UINT32` | `360` | Geant4 polyhedron rotation samples; valid range is 8 to 4096 |
| `macro` | — | Geant4 macro file; required for a build without UI |

Built-in macros:

| File | Purpose | Analysis file |
| --- | --- | --- |
| `scripts/run_optical_test.mac` | Emit one deterministic optical photon from inside the crystal | `run_optical_test.root` |
| `scripts/run_cpu_benchmark.mac` | Emit a 5 MeV electron beam for the single-core CPU benchmark (1000 events) | `run_cpu_benchmark.root` |
| `scripts/run_eminus_regression.mac` | Emit a 5 MeV electron beam for the CPU/GPU regression (100000 events) | `run_eminus_regression.root` |
| `scripts/vis.mac` | Interactive geometry and track visualization | `vis.root` |

ROOT files are written to the current working directory using each macro's `/analysis/setFileName` value.

## Performance benchmark

`test/regression_test.sh` is the single driver for performance measurement and CPU/GPU regression checks. For concise reference, it uses these configuration names:

- `CPU-6T`: a CPU run with 6 Geant4 workers that produces the regression reference; its estimated performance time is derived from the 1T CPU benchmark.
- `GPU-1T`: a GPU/OptiX run with 1 Geant4 worker.
- `GPU-6T`: a GPU/OptiX run with 6 Geant4 workers.

The driver runs them in this order:

1. Generate or load the cached `CPU-6T` reference.
2. Measure wall time and save ROOT output for `GPU-1T` and `GPU-6T`.
3. Compare both GPU outputs with the same `CPU-6T` reference for `Edep`, `nOptPho`, TOF, and sensor occupancy.
4. Compare performance with matching worker counts: `GPU-1T` against estimated `CPU-1T`, and `GPU-6T` against estimated `CPU-6T`:

   ```text
   GPU-1T speedup = estimated CPU-1T time / GPU-1T wall time
   estimated CPU-6T time = estimated CPU-1T time / 6
   GPU-6T speedup = estimated CPU-6T time / GPU-6T wall time
   ```

The driver also runs the small one-worker CPU benchmark from `run_cpu_benchmark.mac`; the 6T CPU performance time is estimated by assuming linear scaling from 1T. Run the complete workflow directly with:

~~~bash
test/regression_test.sh --build-dir build
~~~

Summaries, reports, and comparison plots are written under `build/test/regression/`. Set `G4GO_PERF_DIAGNOSTICS=1` for detailed timings from both GPU runs.

## Detector model

The current `DetectorConstruction` builds a single-crystal optical detector cell:

- A `3 cm × 3 cm × 8 cm` `G4_CESIUM_IODIDE` crystal.
- Crystal optical properties including refractive index, absorption length, scintillation spectrum, scintillation yield, and time constants.
- A silicone-grease coupling layer, epoxy window, and a `3 mm × 3 mm × 0.1 mm` SiPM connected to the crystal front face.
- Optical surfaces and detection-efficiency curves between the crystal, wrapping layer, world volume, and SiPM.

Material properties and optical surfaces are currently defined in `src/detector/DetectorConstruction.cpp`.

## ROOT output

ROOT files contain two trees. Tree names use PascalCase and branch names use lowerCamelCase; `Edep` and `nOptPho` retain the project conventions.

| Tree | Branch | Meaning |
| --- | --- | --- |
| `CrystalHit` | `eventID` | Geant4 event ID |
| `CrystalHit` | `moduleID` | Crystal module ID |
| `CrystalHit` | `Edep` | Crystal energy deposition |
| `CrystalHit` | `nOptPho` | Number of SiPM-detected photons in the event |
| `SensorHit` | `eventID` | Geant4 event ID |
| `SensorHit` | `sensorID` | SiPM copy number |
| `SensorHit` | `timeOfFlight` | Photon arrival time |

## Architecture

~~~text
G4GO/
├── cmake/                  # CMake helper scripts
├── include/g4go/
│   ├── detector/           # Public detector interfaces
│   ├── optical/            # Backend-independent optical data and interfaces
│   └── simulation/         # Public Geant4 action interfaces
├── scripts/                # Geant4 macros
├── src/
│   ├── detector/           # Geometry, materials, and sensitive detectors
│   ├── optical/
│   │   ├── geant4/         # Event adapter, scene exporter, and batch service
│   │   └── optix/          # OptiX host/device transport
│   └── simulation/         # Run, event, and analysis actions
└── test/                   # Unit, smoke, and regression tests
~~~

Geant4 remains the geometry source of truth; the scene exporter converts solids into OptiX meshes while preserving placement, material, surface, copy-number, and parent information.

## GPU optical scope and limitations

The GPU backend currently supports:

- `polished` and `ground` finishes with the `glisur` and `unified` surface models.
- `dielectric_metal` and `dielectric_dielectric` surface types.
- Fresnel reflection, refraction, and total internal reflection with S/P polarization components.
- `REFLECTIVITY`, `TRANSMITTANCE`, and `EFFICIENCY` in the absorption path.
- GLISUR polish, UNIFIED sigma-alpha, specular lobe/spike, and backscatter parameters.

Scene export explicitly rejects currently unsupported Rayleigh, Mie, WLS, LUT, DAVIS, dichroic, coated surface types/models, and painted finishes. Photons reaching `--max-bounces` are counted as `truncated`; invalid states are counted as `invalid`. Both counters appear in GPU backend run statistics.

## Tests

Run the fast tests after building:

~~~bash
ctest --test-dir build --output-on-failure -L 'unit|smoke'
~~~

| CTest | Labels | Coverage |
| --- | --- | --- |
| `g4go_optical_boundary` | `unit;cpu` | Fresnel, Brewster angle, total internal reflection, surface probabilities, and Lambertian directions |
| `g4go_smoke_auto` | `smoke;integration;auto` | Single-photon end-to-end initialization and transport |
| `g4go_noptpho_regression` | `regression;gpu;slow` | `GPU-1T` and `GPU-6T` compared separately against a cached or newly generated `CPU-6T` reference for `Edep`, `nOptPho`, TOF, and sensor occupancy |

### CPU/GPU regression

The CTest test `g4go_noptpho_regression` is the project test entry point for the same `CPU-6T`, `GPU-1T`, and `GPU-6T` workflow:

~~~bash
ctest --test-dir build --output-on-failure \
  -R '^g4go_noptpho_regression$'
~~~

The test requires both GPU comparisons and their ROOT reports, summaries, and plots to pass. To stream the complete log:

~~~bash
bash build/test/regression_test.sh --build-dir build --verbose
~~~

Each run stores its aggregate summary and timestamped artifacts under `build/test/regression/`; individual reports are under `comparisons/gpu_1t/` and `comparisons/gpu_6t/`, with their plots in the corresponding `figures/` directories and logs in `logs/`.

## WSL2 OptiX runtime troubleshooting

WSL2 uses the Windows host NVIDIA driver and a CUDA Toolkit installed inside WSL. See the [CUDA on WSL User Guide](https://docs.nvidia.com/cuda/wsl-user-guide/index.html). A missing `optixQueryFunctionTable` symbol produces:

~~~text
optixInit failed: OPTIX_ERROR_ENTRY_SYMBOL_NOT_FOUND
~~~

Check the driver, toolkit, and OptiX loader:

~~~bash
nvidia-smi
nvcc --version
nm -D /usr/lib/wsl/lib/libnvoptix.so.1 | rg optixQueryFunctionTable
~~~

Update the Windows NVIDIA driver when the symbol is missing, run `wsl --shutdown` in PowerShell, reopen WSL, and retry the GPU smoke test.
