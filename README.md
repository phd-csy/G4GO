G4GO uses Geant4 as its physics and geometry foundation and CUDA/OptiX to accelerate optical-photon transport.

The project targets single-crystal optical detector cells. It provides unified CPU/GPU optical backends, a Geant4 event adapter, and ROOT ntuple output. The GPU backend performs batched optical-photon transport while Geant4 continues to handle particle interactions, geometry, material properties, event management, and result writing.

## Features

- Detector construction, primary-particle generation, energy deposition, and CPU optical transport with Geant4.
- GPU optical-photon transport with CUDA and NVIDIA OptiX 9.1.
- `auto`, `cpu`, and `gpu` backend selection.
- ROOT ntuple output for `CrystalHit` and `SensorHit`.
- Optical-boundary unit tests, an end-to-end smoke test, and CPU/GPU optical regression tests with TOF, sensor occupancy, and thread-determinism checks.

## Backends

| Backend | Optical-photon processing | Use cases | Failure behavior |
| --- | --- | --- | --- |
| `auto` | Prefer OptiX and fall back to Geant4 when initialization fails | General runs and smoke tests | Keep a warning and continue with CPU |
| `cpu` | Native Geant4 optical tracking | Baselines and systems without an NVIDIA GPU | Report Geant4 errors directly |
| `gpu` | Capture optical photons generated by Geant4 and transport them with OptiX | GPU validation, performance tests, and regression tests | Fail directly when OptiX is unavailable |

The GPU backend uses an asynchronous event-aggregation pipeline. Geant4 workers submit events to a shared queue; an independent GPU executor aggregates multiple events and launches OptiX. Results are returned to the originating worker by event ID and written to ROOT through the Geant4 analysis manager.

## Dependencies

### Core build

| Dependency | Requirement | Purpose |
| --- | --- | --- |
| CMake | 3.24 or newer | Configure and build |
| C++ compiler | C++20 support | Compile host code |
| Geant4 | 11.4.2 or compatible | Physics, geometry, events, and analysis |
| Git and network access | Available during the first configure step | Fetch CLI11 with `FetchContent`; fetch OptiX headers when enabled |

### GPU backend

- An NVIDIA GPU and an NVIDIA driver newer than R590. The OptiX runtime is provided by the NVIDIA driver.
- CUDA Toolkit 12.0 or newer, including `nvcc` and `bin2c`.
- OptiX 9.1 development headers fetched by CMake from `NVIDIA/optix-dev`; the full OptiX SDK is optional for G4GO.
- `G4GO_CUDA_ARCHITECTURE` matching the target GPU compute capability.

### Testing and result inspection

- Bash for CPU/GPU regression orchestration.
- ROOT command-line tools for regression comparison; `rootls` can inspect output files.
- `clang-format` is optional; when detected, CMake creates formatting targets.

## Build

### Enable OptiX

~~~bash
cmake -S . -B build \
  -DG4GO_BUILD_UIVIS=OFF \
  -DG4GO_ENABLE_OPTIX=ON
cmake --build build -j
~~~

The configure step checks for a CUDA compiler, the CUDA Toolkit, `bin2c`, and OptiX headers. The full OptiX SDK is not required because CMake fetches the development headers. When all dependencies are available, the OptiX backend is built; otherwise `g4go` is still generated with the Geant4 backend.

`G4GO_CUDA_ARCHITECTURE` uses CUDA's `compute_XX` numeric value. For example, use the following configuration for `compute_89`:

~~~bash
cmake -S . -B build \
  -DG4GO_BUILD_UIVIS=OFF \
  -DG4GO_ENABLE_OPTIX=ON \
  -DG4GO_CUDA_ARCHITECTURE=89
cmake --build build -j
~~~

### Geant4 backend only

~~~bash
cmake -S . -B build \
  -DG4GO_BUILD_UIVIS=OFF \
  -DG4GO_ENABLE_OPTIX=OFF
cmake --build build -j
~~~

### Common CMake options

| Option | Default | Description |
| --- | --- | --- |
| `G4GO_BUILD_UIVIS` | `ON` | Build Geant4 UI and visualization support |
| `G4GO_ENABLE_OPTIX` | `ON` | Try to build the CUDA/OptiX backend |
| `G4GO_CUDA_ARCHITECTURE` | `120` | CUDA compute architecture for the OptiX device program |
| `G4GO_ENABLE_FORMAT_TARGETS` | `ON` | Detect and create clang-format targets |
| `G4GO_ENABLE_CLANG_TIDY` | `OFF` | Enable clang-tidy during compilation |
| `BUILD_TESTING` | `ON` | Register CTest tests |

During configuration, `scripts/` is copied to `build/scripts/` and test files are copied to `build/test/`. Re-run CMake after changing these files to synchronize the build directory.

Install the executable with:

~~~bash
cmake --install build --prefix /path/to/prefix
~~~

## Quick start

Run the single-photon optical test macro from the build directory:

~~~bash
cd build
./g4go --backend auto scripts/run_optical_test.mac
~~~

Run an explicit CPU or GPU backend:

~~~bash
cd build
./g4go --backend cpu --threads 1 scripts/run_optical_test.mac
./g4go --backend gpu scripts/run_optical_test.mac
~~~

A successful GPU backend run includes:

~~~text
[g4go] optical backend: gpu, ...
~~~

With `G4GO_BUILD_UIVIS=ON`, start interactive visualization from the directory containing `vis.mac`:

~~~bash
cd build/scripts
../g4go
~~~

## Command-line interface

~~~text
g4go [OPTIONS] [macro]
~~~

| Option | Default | Description |
| --- | --- | --- |
| `-h, --help` | — | Show help |
| `--backend auto\|cpu\|gpu` | `auto` | Select the optical-photon transport backend |
| `--seed UINT64` | `42` | Set Geant4 and OptiX random seeds |
| `--threads UINT32` | `0` | Number of Geant4 workers; `0` uses the detected CPU core count |
| `--batch-photons UINT32` | `1000000` | Target photon count per GPU batch |
| `--max-photons UINT32` | `5000000` | Maximum photons captured per event |
| `--max-bounces UINT32` | `4096` | Maximum boundary interactions per photon |
| `--mesh-rotation-steps UINT32` | `360` | Geant4 polyhedron rotation samples; valid range is 8 to 4096 |
| `macro` | — | Geant4 macro file; required for a build without UI |

Built-in macros:

| File | Purpose | Analysis file |
| --- | --- | --- |
| `scripts/run_optical_test.mac` | Emit one deterministic optical photon from inside the crystal | `run_optical_test.root` |
| `scripts/run_beam_eminus.mac` | Emit a 5 MeV electron beam from in front of the crystal for 2000 events | `run_beam_eminus.root` |
| `scripts/vis.mac` | Interactive geometry and track visualization | `vis.root` |

ROOT files are written to the current working directory. The output name is selected by each macro's `/analysis/setFileName` command; the Geant4 analysis manager may omit an empty file when an event produces no writable ntuple records. Inspect beam-run output with:

~~~bash
cd build
./g4go --backend cpu scripts/run_beam_eminus.mac
rootls -t run_beam_eminus.root
~~~

## Detector model

The current `DetectorConstruction` builds a single-crystal optical detector cell:

- A `3 cm × 3 cm × 8 cm` `G4_CESIUM_IODIDE` crystal.
- Crystal optical properties including refractive index, absorption length, scintillation spectrum, scintillation yield, and time constants.
- A silicone-grease coupling layer, epoxy window, and a `3 mm × 3 mm × 0.1 mm` SiPM connected to the crystal front face.
- Optical surfaces and detection-efficiency curves between the crystal, wrapping layer, world volume, and SiPM.

Material properties and optical surfaces are currently defined in `src/detector/DetectorConstruction.cpp`.

## ROOT output

ROOT files contain two trees. Tree names use PascalCase and branch names use lowerCamelCase; `Edep` and `nOptPho` retain the project conventions.

| Tree | Branch | Meaning |
| --- | --- | --- |
| `CrystalHit` | `eventID` | Geant4 event ID |
| `CrystalHit` | `moduleID` | Crystal module ID |
| `CrystalHit` | `Edep` | Crystal energy deposition |
| `CrystalHit` | `nOptPho` | Number of SiPM-detected photons in the event |
| `SensorHit` | `eventID` | Geant4 event ID |
| `SensorHit` | `sensorID` | SiPM copy number |
| `SensorHit` | `timeOfFlight` | Photon arrival time |

## Architecture

~~~text
G4GO/
├── cmake/                  # CMake helper scripts
├── include/g4go/
│   ├── detector/           # Public detector interfaces
│   ├── optical/            # Backend-independent optical data and interfaces
│   └── simulation/         # Public Geant4 action interfaces
├── scripts/                # Geant4 macros
├── src/
│   ├── detector/           # Geometry, materials, and sensitive detectors
│   ├── optical/
│   │   ├── geant4/         # Event adapter, scene exporter, and batch service
│   │   └── optix/          # OptiX host/device transport
│   └── simulation/         # Run, event, and analysis actions
└── test/                   # Unit, smoke, and regression tests
~~~

CMake builds `g4go_optical_core`, the optional `g4go_optical_optix`, `g4go_optical_geant4`, `g4go_detector`, and `g4go_simulation` static libraries, then combines them into the `g4go` executable.

Geant4 is the geometry truth source. The scene exporter uses `CreatePolyhedron()` to convert solids into triangle meshes while preserving placement, material, surface, copy number, and parent topology. Meshes for identical `G4VSolid` objects can be reused while each physical volume retains an independent OptiX instance.

## GPU optical scope and limitations

The GPU backend currently supports:

- `polished` and `ground` finishes with the `glisur` and `unified` surface models.
- `dielectric_metal` and `dielectric_dielectric` surface types.
- Fresnel reflection, refraction, and total internal reflection with S/P polarization components.
- `REFLECTIVITY`, `TRANSMITTANCE`, and `EFFICIENCY` in the absorption path.
- GLISUR polish, UNIFIED sigma-alpha, specular lobe/spike, and backscatter parameters.

Scene export explicitly rejects currently unsupported Rayleigh, Mie, WLS, LUT, DAVIS, dichroic, coated surface types/models, and painted finishes. Photons reaching `--max-bounces` are counted as `truncated`; invalid states are counted as `invalid`. Both counters appear in GPU backend run statistics.

The default `--mesh-rotation-steps 360` uses a correctness-first setting. Geometry profiling should evaluate mesh error, triangle count, GAS build time, GPU memory, and transport time together.

## Tests

Run the fast tests after building:

~~~bash
ctest --test-dir build --output-on-failure -L 'unit|smoke'
~~~

| CTest | Labels | Coverage |
| --- | --- | --- |
| `g4go_optical_boundary` | `unit;cpu` | Fresnel, Brewster angle, total internal reflection, surface probabilities, and Lambertian directions |
| `g4go_smoke_auto` | `smoke;integration;auto` | Single-photon end-to-end initialization and transport |
| `g4go_noptpho_regression` | `regression;cpu;gpu;slow` | Single-core CPU, all-core CPU, and GPU `CrystalHit.nOptPho` comparison |

Run all tests:

~~~bash
ctest --test-dir build --output-on-failure
~~~

### CPU single-core/all-core and GPU `nOptPho` regression

~~~bash
(
  cd build
  ctest --no-label-summary --output-on-failure \
    -R '^g4go_noptpho_regression$'
)
~~~

The regression driver runs `scripts/run_beam_eminus.mac` with a single-core CPU run, an all-core CPU run, and an all-core GPU run. The ROOT comparison checks `nOptPho`, `SensorHit` detection counts, time-of-flight summaries, and a 64-bin sensor occupancy map. A separate deterministic optical-photon macro then runs GPU transport with 1, 2, 4, and 8 Geant4 worker threads and compares the generated, absorbed, escaped, and detected statistics. By default, “all-core” uses all detected physical cores; pass `--threads N` to override the worker count. Normal mode prints phase summaries while preserving complete child-process output in stage logs. Use `--verbose` when running the driver directly to stream child-process output. The statistical comparison uses the all-core CPU result as the Geant4 reference and reports GPU speedups relative to both CPU runs. The GPU run explicitly uses `--backend gpu`, so missing GPU, OptiX runtime, driver, or ROOT causes the test to fail while preserving diagnostic files.

The command omits CTest's `-V` option. `--no-label-summary` hides the repeated label timing table, and `--output-on-failure` prints test output only when the test fails. To inspect the full regression stream, run:

~~~bash
bash build/test/regression_test.sh --build-dir build --verbose
~~~

The ROOT comparison macro `test/TestOpticalTransport.cxx` uses unweighted `Chi2TestX(..., "UU P OF")` for the `nOptPho` distribution and checks the total photon count. The test fails when `Z > 5`, the chi-square condition is invalid, or the relative total-yield difference exceeds 10%. Results with `3 < Z <= 5` are marked `SUSPICIOUS`; other valid results pass.

Artifacts are stored in `build/test/regression/noptpho_<timestamp>/`:

- `noptpho_cpu_single.root`, `noptpho_cpu_all.root`, `noptpho_gpu.root`: single-core CPU, all-core CPU, and GPU input data.
- `noptpho_comparison.png`, `noptpho_regression_report.root`: Distribution, pull, and statistical reports.
- `regression_result.txt`: Conclusion, three wall-clock times, and GPU speedups relative to both CPU runs.
- `cpu_single.log`, `cpu_all.log`, `gpu.log`, `comparison.log`, and `gpu_determinism.log`: Complete stage logs; `regression.log` contains orchestration output and streamed child output in verbose mode.

## WSL2 OptiX runtime troubleshooting

WSL2 CUDA and OptiX runtime support depends on Windows host NVIDIA driver mappings. For environment preparation, see the [CUDA on WSL User Guide](https://docs.nvidia.com/cuda/wsl-user-guide/index.html). Install the CUDA Toolkit inside WSL; the NVIDIA display driver is supplied by the Windows host.

In some WSL2 environments, `/usr/lib/wsl/lib/libnvoptix.so.1` is only a loader shim and lacks `optixQueryFunctionTable`, which produces:

~~~text
optixInit failed: OPTIX_ERROR_ENTRY_SYMBOL_NOT_FOUND
~~~

Inspect the current environment:

~~~bash
nvidia-smi
nvcc --version
ls -lh /usr/lib/wsl/lib/libnvoptix.so.1
nm -D /usr/lib/wsl/lib/libnvoptix.so.1 | rg optixQueryFunctionTable
~~~

You can extract the OptiX user-space libraries from an NVIDIA Linux display-driver package compatible with the host driver. Place `libnvoptix.so.*`, `libnvidia-rtcore.so.*`, `libnvidia-ptxjitcompiler.so.*`, `libnvidia-gpucomp.so.*`, and `nvoptix.bin` in a user directory, and put that directory before `/usr/lib/wsl/lib` in `LD_LIBRARY_PATH`. This extracts the libraries without installing a Linux display driver inside WSL.

Validate the custom runtime:

~~~bash
export G4GO_OPTIX_RUNTIME=/path/to/extracted/optix-runtime

nm -D "$G4GO_OPTIX_RUNTIME/libnvoptix.so.1" \
  | rg optixQueryFunctionTable

LD_LIBRARY_PATH="$G4GO_OPTIX_RUNTIME:/usr/lib/wsl/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
  ldd "$G4GO_OPTIX_RUNTIME/libnvoptix.so.1" \
  | rg 'nvoptix|rtcore|ptxjit|gpucomp|not found'

./build/g4go --backend gpu build/scripts/run_optical_test.mac
~~~

After updating the Windows NVIDIA driver or WSL mapping, run `wsl --shutdown` in PowerShell, reopen WSL, and verify the dynamic-library search order again.

## Contributing

When submitting an issue or pull request, include the problem context, reproduction steps, backend, Geant4/CUDA/OptiX versions, and validation results. Keep module boundaries intact, add tests directly related to the change, and run the following before committing:

~~~bash
cmake --build build --target g4go-format-check
ctest --test-dir build --output-on-failure -L 'unit|smoke'
~~~

Commit messages follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/), for example:

~~~text
fix(optical): preserve photon polarization across reflection
~~~
